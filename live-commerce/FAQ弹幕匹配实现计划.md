# FAQ 弹幕匹配 — 实现计划

> **目标**：让数字人主播能「回应弹幕」——观众问什么，画面切到对应的已渲染回答片段。
>
> **本文档是实施计划，不是实现**。含已实测的关键数据、架构决策、模块划分、分阶段步骤与验收标准。
>
> 核验日期：2026-09-16。标 ✅ 的是**已实测**，标 ⚠️ 的是**推断或未验证**。

---

## 0. 一句话方案

**不做实时生成，做预渲染 + 匹配切换。**

```
离线：products.json 的每一条 faq  →  渲染成独立片段  →  faq_index.json
                                        （含关键词与向量）
在线：弹幕流  →  匹配器  →  命中则插播对应片段  →  未命中则记日志，回主播放列表
```

---

## 1. 为什么必须预渲染（这不是选择，是约束）

| 实测项 | 数值 | 来源 |
|---|---|---|
| 单条口播渲染耗时（冷态） | **41.9 秒** | `GET /api/v1/tasks` 实读 |
| 单条口播渲染耗时（热态） | **17~18 秒** | 同上 |
| 服务并发 | **worker = 1，串行** | `config.py:33`，注释「单卡只能串行跑 GPU 推理」 |

**结论**：观众问一句话，画面至少要 **17 秒后**才有回应，且期间**所有其他请求都被堵住**。

> 🔴 任何「弹幕 → LLM 生成 → TTS → 口型 → 出片」的实时链路都不可行。这不是调参能解决的，
> 是单卡串行推理的架构约束。

**唯一的可行路径**：把「实时」降级为「预渲染 + 亚秒级切换」。

## 2. 关键技术验证（✅ 已实测，这决定架构）

### 2.1 ffmpeg 重启代价 1.8 秒 → 不能 kill/restart 切片段

| 测量 | 结果 |
|---|---|
| `ffmpeg -re -i x.mp4 -c copy -f flv out` 启动到首字节 | **1803 / 1815 / 1803 ms**（三次高度一致） |
| `-re` 限速 | ✅ 生效（3 秒推 256KB，全片 17.5MB） |

**含义**：如果每次切片段都 kill 掉 ffmpeg 再起一个新的，**每次插播会有约 2 秒黑屏**。
在直播里这是明显的「卡顿」，且推流断开可能触发平台的断流保护。

### 2.2 TS 字节级拼接可行 → 改用 FIFO 喂流，切换零中断

| 测量 | 结果 |
|---|---|
| 3 个片段转 MPEG-TS 后 `cat a.ts b.ts c.ts > joined.ts` | ✅ 拼接成功 |
| 重封装成 mp4 后的时长 | **31.095s**，与 4.11+11.75+15.29=**31.15s** 吻合 |
| 拼接产物音轨 | ✅ 峰值 22896，正常 |

**含义**：TS 是**流式容器**，字节级首尾相接即可连续播放。所以：

```
              ┌─────────────────────────────────────┐
弹幕命中了 →  │  往 FIFO 里写 B.ts 的字节            │
              │  （正在写的 A.ts 写完当前包后接上）  │
              └─────────────────────────────────────┘
                          ↓
        ffmpeg -i /tmp/live.fifo -c copy -f flv rtmp://...
                          ↑
                   一个**常驻不重启**的进程
```

**切换代价 = 写入缓冲的字节数**，量级在 **几十毫秒**，肉眼不可见。
⚠️ 精确延迟**未实测**（需要真实 RTMP 端点才能测端到端延迟）。

> 📌 **注意**：raw `.ts` 的 `ffprobe` 时长读数**不可靠**（无全局索引，ffprobe 会按首段 PES 估算，
> 实测报 15.36s 而实际内容 31.1s）。**验证一律以重封装后的 mp4 时长为准**。

## 3. 架构

```
┌─ 离线 ────────────────────────────────────────────────────────┐
│  products.json                                                │
│    └─ faq[] ──→ faq_build.py ──→ build/faq/<sku>-faqN.mp4     │
│                       │                  + .ts（供 FIFO 喂）  │
│                       └──→ faq_index.json（关键词 + 向量）    │
└───────────────────────────────────────────────────────────────┘
                              ↓
┌─ 在线 ────────────────────────────────────────────────────────┐
│                                                               │
│  danmaku.py ──→ matcher.py ──┬─ 命中 ──→ player.py 插播       │
│  （多源适配）   （关键词+向量）│              （FIFO 喂 ffmpeg） │
│                              └─ 未命中 ──→ unanswered.log     │
│                                    ↓                          │
│                              回主播放列表继续                  │
└───────────────────────────────────────────────────────────────┘
                              ↓
                    ffmpeg 常驻进程 → RTMP
```

## 4. 模块设计

### 4.1 `faq_build.py` — FAQ 预渲染

**职责**：把 `products.json` 里所有 `faq[]` 渲染成独立片段，并建索引。

```
输入：products.json + 数字人档案
输出：
  build/faq/<sku>-faq<N>.mp4     片段（可直接播）
  build/faq/<sku>-faq<N>.ts      同内容 TS 版（供 FIFO 无缝喂流）
  build/faq/faq_index.json       索引
```

**`faq_index.json` 结构**：

```json
{
  "built_at": "2026-09-16 22:00:00",
  "profile_id": "xiaomei",
  "entries": [
    {
      "id": "MZ001-faq1",
      "sku": "MZ001",
      "question": "敏感肌能用吗",
      "keywords": ["敏感肌", "敏感", "过敏", "泛红"],
      "answer_text": "配方不含酒精和香精，但敏感肌建议先在耳后做局部测试…",
      "video": "MZ001-faq1.mp4",
      "ts": "MZ001-faq1.ts",
      "duration": 9.6,
      "embedding": [0.123, -0.456, ...],
      "cooldown_seconds": 120,
      "play_count": 0
    }
  ]
}
```

**关键词从哪来**（三级递进）：

1. **自动**：对 `question` 分词，取名词/动词性词汇
2. **同义扩展**：维护一份小同义词表（`敏感肌`/`敏感`/`过敏`；`多少钱`/`价格`/`几块`）
3. **人工补充**：商品资料里加 `faq[].keywords` 字段，优先级最高

**预渲染成本**（按 3 SKU × 5 FAQ ≈ 15 段估算）：

| | 数值 |
|---|---|
| 每段约 20~30 秒 | 实测（`live_build.py` 25 段用了 11.2 分钟） |
| 15 段总耗时 | **约 6~8 分钟** |
| 增量渲染 | ✅ 已有产物跳过（复用 `live_build.py` 的断点续跑逻辑） |

> 💡 **新增 FAQ 只需重渲该条**，不需要全量重建。靠 `id` 判断。

### 4.2 `danmaku.py` — 弹幕接入

> ⚠️ **这是全项目风险最高、也最不该由本系统解决的问题。**

**现实情况**：

| 接入方式 | 可行性 | 风险 |
|---|---|---|
| 抖音/淘宝/视频号 **官方开放平台** | 需企业资质 + 审核 | 低，但门槛高、审批慢 |
| 第三方开源库（逆向抓取） | 技术上可行 | 🔴 **有封号风险、频繁失效、可能违反平台协议** |
| 人工/模拟输入 | 立即可用 | 无 |

**架构决策**：**本系统不内置任何平台抓取实现**，只定义一个**弹幕输入接口**：

```
弹幕源（任意）→ 统一消息格式 → 匹配器
```

**统一消息格式**：

```json
{"ts": 1789564800.123, "user": "张三", "text": "敏感肌能用吗", "source": "douyin"}
```

**支持三种接入**（按实现顺序）：

1. **stdin / 文件 tail**（阶段一，用于开发与测试）
   ```bash
   echo '{"text":"敏感肌能用吗"}' | python player.py --stdin
   tail -f danmaku.jsonl | python player.py --stdin
   ```
2. **本地 HTTP 回调**（阶段二，让外部程序 POST 进来）
3. **WebSocket**（阶段三，接真实弹幕源）

> ✅ 这样设计的价值：**平台接入是可替换的插件**。第三方库失效或平台政策变化时，
> 只需换一个「往 HTTP 端点 POST」的小脚本，播放器与匹配器**完全不用动**。

**弹幕清洗**（`danmaku.py` 内）：

| 处理 | 原因 |
|---|---|
| 去 `@昵称`、去表情符号 | 干扰匹配 |
| 去空白、全角转半角 | 统一归一化（复用 `compliance.normalize`） |
| 过滤纯表情/单字/超长 | 无意义输入 |
| 过滤广告（含 URL、微信号） | 直播间常见 |
| 过滤违规词 | 复用 `compliance.check()`，命中则不响应 |

### 4.3 `matcher.py` — 匹配器

**两段式**（快路径 + 兜底路径）：

```
输入弹幕 "敏感肌可以用吗"
  │
  ├─ ① 归一化
  │
  ├─ ② 关键词精确命中（倒排索引，O(1)）
  │     命中 → 直接返回，<1ms
  │
  └─ ③ 未命中 → 向量余弦相似度，取 top1
        相似度 ≥ 阈值 τ → 返回
        否则 → 返回 None（未命中）
```

**为什么要两段**：

| | 关键词 | 向量 |
|---|---|---|
| 速度 | <1ms | ~10ms（本地）/ ~200ms（云端） |
| 精确性 | 高（配了词就必中） | 中（有语义漂移） |
| 覆盖率 | 低（没配的词不中） | 高（同义表述能中） |
| 可控性 | 高（能预测） | 低（可能误匹配） |

关键词扛住高频问题（占弹幕大头），向量兜住长尾表述。**向量结果必须过阈值**，
宁可漏答也不能答非所问——直播间答错比不答更伤。

**阈值 τ 的取值**：⚠️ 未实测。建议**先用 0.75 起步**，再根据 `unanswered.log`
和误匹配情况调整。**必须有一份标注集来调**（见 §7 验收）。

**冷却机制**（防止刷屏）：

```python
# 同一个片段在上次播放后 cooldown_seconds 内不重复插播
if now - entry["last_played_at"] < entry["cooldown_seconds"]:
    return None      # 视为未命中，但不记 unanswered.log
```

默认冷却 **120 秒**，可按 FAQ 单独配（促销类短一点，使用说明类长一点）。

**插播节流**：全局限制「每 N 秒最多插播一次」，避免弹幕轰炸时画面一直被切。
建议 **30 秒**。

### 4.4 `player.py` — 播放器（FIFO 喂流）

**核心**：一个常驻 ffmpeg + 一条 FIFO + 一个播放队列。

```python
# 伪代码骨架
os.mkfifo(FIFO)
ffmpeg = Popen([FF, "-re", "-i", FIFO, "-c", "copy", "-f", "flv", RTMP_URL])

def feed(ts_path):
    """把 TS 文件字节写进 FIFO。写完当前文件自然衔接下一个。"""
    with open(ts_path, "rb") as f, open(FIFO, "wb") as fifo:
        shutil.copyfileobj(f, fifo, length=64*1024)

# 主循环
while True:
    hit = matcher.try_match(peek_queue())      # 非阻塞看一眼有没有命中
    feed(hit.ts if hit else next_main_playlist_ts())
```

**关键实现点**：

| 点 | 说明 |
|---|---|
| FIFO 必须以**二进制**打开 | `open(FIFO, "wb")` |
| 写 FIFO 会**阻塞**直到有读者 | ffmpeg 必须先启动，否则 `open()` 就卡住 |
| ffmpeg 挂了要能重启 | 监控进程存活，重启后从主列表继续（会丢几秒，可接受） |
| TS 片段必须**同码流参数** | 都从同一条管线产出，天然一致（实测 25 段拼接零偏差） |
| 主播放列表也要转 TS | 用 `playlist.ts` 而不是 `playlist.mp4` 喂流 |

**启动顺序**（容易错）：

```
1. 建 FIFO
2. 启动 ffmpeg 读 FIFO（它会阻塞等数据）
3. 开始往 FIFO 写第一个片段
```
顺序反了会死锁。

### 4.5 未命中闭环

**这是「越用越好」的关键**，不能省。

```
未命中弹幕 ──→ unanswered.log（JSONL）
                    ↓
            人工定期审核（每天/每周）
                    ↓
      有价值的问题 ──→ 补进 products.json 的 faq[]
                    ↓
            faq_build.py --incremental（只渲新增）
                    ↓
              下次直播就能答了
```

**`unanswered.log` 格式**：

```json
{"ts": 1789564800.1, "text": "这个和XX家的比怎么样", "top1_score": 0.61, "top1_id": "MZ001-faq1"}
```

`top1_score` 和 `top1_id` 用来判断：是**真的没这条 FAQ**（score 很低），
还是**阈值定高了**（score 接近 τ）。**前者补内容，后者调阈值。**

## 5. 匹配算法选型

### 5.1 Embedding 来源对比

| 方案 | 体积 | 质量 | 依赖 | 推荐 |
|---|---|---|---|---|
| **A. sentence-transformers + `text2vec-base-chinese`** | ~400 MB 下载 | 好 | 需 `pip install sentence-transformers` | ⭐ **推荐** |
| **B. 复用已有 `chinese-roberta-wwm-ext-large`** | **0（已在位）** | 一般 | 无（transformers 已装） | 零依赖降级方案 |
| **C. 云端 embedding API** | 0 | 最好 | 需网络+key | 已接 LLM 的话首选 |
| D. 纯关键词，不要向量 | 0 | 覆盖窄 | 无 | **阶段一的起点** |

> 📌 **方案 B 值得一试**：`chinese-roberta-wwm-ext-large` 已经在
> `GPT_SoVITS/pretrained_models/`（621MB），`transformers 4.39.2` 也已装。
> 它不是句向量模型，需要用 mean-pooling 手工取向量，效果不如 A，但**零下载零依赖**。
> ⚠️ 效果**未实测**，建议先用 B 快速跑通，再决定要不要换 A。

### 5.2 推荐路线

```
阶段一：纯关键词（不引入任何模型）
          ↓ 跑通全链路，收集真实弹幕
阶段二：加向量兜底（先用方案 B，零依赖）
          ↓ 用 unanswered.log 评估召回率
阶段三：若召回不足，换方案 A 或 C
```

**不要一上来就上向量。** 关键词能覆盖电商直播间的绝大多数高频问题
（「多少钱」「怎么用」「能用多久」），而且**完全可预测**——出问题好排查。

#### 2.5 遗留问题：插播点的 PTS 不连续（阶段一已知）

**现象**：每次 FAQ 插播会给 muxer 带来约 **46 条** `non monotonically increasing dts` 警告。

**根因**：FAQ 片段的 PTS 从 0 开始，而插进去的位置上主流已经跑到了几百秒。
muxer 收到的 DTS 突然回退。ffmpeg 会**自动纠正**（日志里 `changing to ...`），
产物仍然有效。

**影响评估**（实测）：

| 指标 | 结果 |
|---|---|
| 视频解码错误 | **0 条** |
| 损坏帧 | **0 条** |
| 音轨连续性 | **全程无断点**（每 2 秒抽检） |
| DTS 警告 | 46 条 / 次插播（muxer 自动纠正，输出可正常解码） |

**已排除的修法**（实测无效，别再试）：

- `-avoid_negative_ts make_zero` → 仍 46 条
- `-max_interleave_delta 0` → 仍 46 条
- `+genpts` → **反而更糟**（见下）

> ⚠️ **`+genpts` 是反效果**。TS 里的时间戳本来就是有效的，重新生成会和它们冲突：
> 实测在**不插播**的情况下，`+genpts` 自己就产生 46 条 DTS 警告，
> 去掉后降到 **0 条**。所以本项目的 ffmpeg 只带 `+igndts`，**不带 `+genpts`**。

**真正的修法**（待做）：在插入时重写 FAQ 片段的 TS 时间戳，加上当前流位置偏移。
需要轻量 TS 解析器（按 188 字节包解析 PES 头、改写 PTS/DTS 字段）。
**工作量估 1 天。**

**为什么阶段一不做**：产物本身可正常解码播放，且**只有接真实 RTMP 才能验证
这段不连续是否真的会导致平台侧问题**——在本地 FLV 上做无意义。等 2.1 拿到
推流地址后再一起验证。

## 7. 验收标准

| 项 | 指标 | 测法 |
|---|---|---|
| **切换延迟** | < 200 ms | 弹幕发出到画面变化的端到端时间 |
| **切换无黑屏** | 无肉眼可见中断 | 逐帧检查切换点 |
| **关键词命中率** | ≥ 80% | 20 条人工弹幕 |
| **向量召回率** | ⚠️ 阶段三再定 | 标注集 |
| **误匹配率** | **< 5%** | 标注集。**这个指标比召回率更重要** |
| **长时间稳定性** | 连续 2 小时不掉流 | 实测 |
| **主列表完整性** | 插播后正确回到原位置 | 记日志比对 |

> 🔴 **误匹配比漏答严重得多。** 观众问「敏感肌能用吗」，主播回答「这个 89 元」，
> 比不回答更伤害信任。**阈值宁可定高。**

### 8.1 🔴 AutoDL 上行带宽实测：不满足推流要求

**测量方法**：向 `speed.cloudflare.com/__up` 上传 10 MB 随机数据 × 5 次。

| 次数 | 上行速度 |
|---|---|
| 1 | 1.1 Mbps |
| 2 | 17.1 Mbps |
| 3 | 8.9 Mbps |
| 4 | 25.5 Mbps |
| 5 | 1.4 Mbps |
| **中位数** | **8.9 Mbps** |
| **最快 / 最慢** | **25.5 / 1.1 Mbps** |
| **波动** | **23.4×** |

**结论：不能在这台 AutoDL 实例上直接推流。**

理由：直播推流要的不是「平均带宽够」，而是**持续稳定的码率供给**。
720p 档需要稳定 2~4 Mbps，而实测 **5 次里有 2 次低于 2 Mbps**，
波动达 23 倍。这会导致推流**反复卡顿、缓冲、甚至断流**——平台侧会判定为劣质流。

**架构后果：渲染与推流必须分离。**

```
┌─ AutoDL（算力）──────────────┐      ┌─ 有稳定带宽的机器 ──────────┐
│  faq_build.py  批量渲染       │      │  player.py  播放 + 推流      │
│  （GPU，带宽不敏感）          │ ───→ │  （CPU，需要稳定上行）       │
└──────────────────────────────┘      └─────────────────────────────┘
        产出 mp4/ts 片段                     拉取片段 → FIFO → RTMP
```

**这个分离其实更合理**：
- AutoDL 只做它擅长的事（GPU 渲染），且渲染是**离线批量**的，对带宽不敏感
- 推流放在**本地机器 / 轻量云服务器**上，带宽便宜且稳定
- 顺带解决了「AutoDL 实例关机就断播」的问题

**对 §4.4 `player.py` 的影响**：

| 原设计 | 调整后 |
|---|---|
| 在 AutoDL 上跑，读本地 FIFO | 在推流机上跑，**通过 HTTP/scp/对象存储拉取片段** |
| 片段在 `build/faq/` | 片段需要**同步机制**（建议：打包上传对象存储，播放器本地缓存） |
| 单机 | 两台机器，需要约定片段清单格式（`faq_index.json` 直接复用） |

> 📌 **好消息**：`player.py` 的核心逻辑（FIFO 喂 TS、匹配、插播）**完全不用改**，
> 只是运行位置和片段来源变了。`faq_index.json` 作为片段清单，天然适合跨机传输。

> ⚠️ **仍需你确认**：推流机准备用哪台？如果也用云服务器，需确认其上行带宽同样达标
> （用同样的方法测一遍即可，5 次 10MB 上传，看波动倍数）。

## 10. 一页速查

```
【AutoDL · 算力】            【推流机 · 稳定带宽】
products.json                danmaku.py ──→ matcher.py
   │                              │
faq_build.py → faq/*.mp4+*.ts     └──→ player.py ──FIFO──→ ffmpeg（常驻）──→ RTMP
   │                   │
   └─ faq_index.json ──┴──── 跨机同步（HTTP/scp/对象存储）────┘

关键数字（已实测）：
  ffmpeg 重启开销      1.8 秒   → 所以用 FIFO 不重启
  TS 字节级拼接        可行     → 所以 FIFO 方案成立
  单条渲染             17~42 秒 → 所以必须预渲染
  15 段 FAQ 预渲染     约 6~8 分钟
  AutoDL 上行          1.1~25.5 Mbps（波动 23.4x）→ 🔴 不能在此推流

关键决策：
  ✅ 预渲染 + 切换，不做实时生成
  ✅ FIFO 喂 TS，不 kill/restart ffmpeg
  ✅ 渲染与推流分离（AutoDL 带宽不达标）
  ✅ 弹幕接入做成可替换插件，不内置平台抓取
  ✅ 匹配先纯关键词，后加向量
  ✅ 阈值宁高勿低（误匹配比漏答更伤）

下一步：确定推流机并测其上行带宽
```
